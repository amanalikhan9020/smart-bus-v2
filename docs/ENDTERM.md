## Сценарий, данные и формула

Цель: выбрать менее загруженный момент поездки и сохранить выбор для последующего просмотра.

```text
Пользователь/гость
  → маршрут + индекс остановки + время
  → общая модель прогноза
  → варианты 0/+30/+60 мин (time + dayOffset)
  → выбор варианта
  → валидация + SmartBusStore.saveTrip
  → localStorage для текущего user.id
  → getTrips → Saved Trips → показатели/диаграмма
```

Соединены прогноз, сравнение, выбор, хранение, список и аналитика сохранённых поездок. Отдельная аналитика симулированного спроса рассчитывает дневной профиль маршрута и не выдаётся за статистику сохранённых поездок. Security объясняет реально реализованные меры; не все страницы обязаны входить в один сценарий.

Исходная модель прогноза сохраняется:

```text
progress = stopIndex / (stopCount - 1)
stopFactor = 18 * sin(pi * progress) + ((stopIndex * 7) mod 13 - 6)
occupancy = clamp(round(base[route] + timeFactor(hour) + stopFactor), 10, 96)
passengers = round(capacity * occupancy / 100)
```

`base`: Bus 10 → 27, 501 → 30, 40 → 29, 53 → 31. Время переводится в `hour + minute/60`. Факторы по часам: до 06 → −12; 06–07 → 5; 07–08 → 20; 08–09 → 30; 09–11 → 15; 11–14 → 10; 14–17 → 15; 17–18 → 25; 18–19 → 35; 19–20 → 28; 20–22 → 12; после 22 → 0. Уровни: <45% низкий, <75% средний, иначе высокий. Это объяснимые правила симуляции, не обученная ML-модель.

Для сравнения меняется только время входа в ту же модель. `dayOffset` хранит переход на следующий день относительно исходного времени; календарная дата поездки не планируется. При равных значениях нельзя обещать менее загруженный вариант.

Средняя загрузка сохранённых поездок — округлённая сумма `occupancy` / количество; максимум — максимальная `occupancy`. Диаграмма показывает округлённую среднюю загрузку сохранённых поездок каждого маршрута. Значения описывают сохранённые прогнозы, а не измеренные пассажиропотоки. PBKDF2-SHA-256 в `storage.js` использует 600 000 итераций и индивидуальную случайную соль; это получение хеша пароля, не шифрование.

## Ограничения и шаги до Final

- Используются тестовые/анонимные/симулированные данные. Нет live CTS, датчиков, гарантий приезда, ML и синхронизации устройств.
- Локальные аккаунты и localStorage не защищают от владельца браузера и редактирования данных через DevTools. Соль/хеш не шифруют поездки; серверной проверки сессии нет. Гостевые данные общие для гостевого профиля этого origin.
- Нормальные legacy-пароли автоматически переходят в PBKDF2, сохраняя ID и поездки. Старый пароль, состоящий только из пробелов (или пустой), требует явной замены через локальную форму восстановления. Такая процедура исправляет слабые локальные записи в текущем браузере; она не является защищённым удалённым сбросом пароля. Эта ветка входит в пройденный 19-й тест.
- Сравнение времени — моделирование спроса, без календарного планирования и реального расписания. Равные прогнозы нормальны.
- Подтвердить версию/требования A3–A4; провести два реальных теста; внести два изменения по feedback и повторить задачи; подтвердить вклад каждого; заполнить и пересобрать PDF.
- Для Final: уточнить модель и оценку её качества, продумать реальные источники данных и серверное хранение/авторизацию при необходимости, повысить доступность на основании обратной связи.
